# Intake and Working Plan

Use this reference for structured service, collection, space, and expertise content. It is also useful for vague requests, internal source material, multi-task content, and requests that require a structural choice. For short microcopy or a line-level revision with all needed facts, skip the plan and draft directly. Use [response-templates.md](response-templates.md) for the response shape.

## Input Classification

Classify the supplied material before deciding how to use it.

| Type | Common signals | How to use it |
| --- | --- | --- |
| Source material | “Here is our service definition,” “source material,” internal goals, workflows, staffing, or metrics | Mine it for facts, tasks, boundaries, and outcomes. Do not polish it sentence by sentence. |
| Rewrite object | “Rewrite,” “revise,” “edit,” “current page,” “proposed message,” or an existing draft | Evaluate it from the Library user’s perspective. Preserve accurate facts; do not preserve framing that obscures the task. |
| Mixed input | Source facts plus existing copy, a proposed structure, or a template | Separate source facts from copy and evaluate each part against the user’s task. |
| Context-only request | A question about approach, audience, structure, or vocabulary | Help the user plan. Ask for source material before drafting if facts are missing. |

If the input type is unclear, assume it is source material and state the assumption in one short line. Even when the user labels material as a rewrite object, continue to test it against UX writing best practices rather than treating its current framing as the required approach.

## Working Plan

Use a plan-first turn by default for structured content. This is the Plan Gate. Show a brief working plan before drafting when one or more of the following is true:

- The audience, primary user task, placement, or desired outcome is missing.
- The source material implies more than one user task.
- The task requires choosing among content molecules or page structures.
- The user’s requested format may not fit the user’s task.
- Key facts, links, policies, or terminology still need verification.

Treat the following as structured content even when the user already names a format: service pages and page sections, service-offering cards, eligibility and access copy, contact and support sections, collection descriptions, space descriptions, expertise pages, and evaluations of those content types. An evaluation, review, or feedback request about one of these content types is also a Plan Gate request.

Skip the plan only when the user has already supplied all of the following:

- User goal or outcome.
- Audience and eligibility.
- Top jobs or tasks.
- Content approach or molecule.
- Material facts, limits, links, and unknowns.

A requested output format alone, such as “turn this into cards,” is not enough to skip the plan. In that case, show the plan first and wait for the user to confirm or revise it.

Use the exact five plan fields in the visible plan:

```markdown
**Goal:** [What the copy should help someone do or decide.]
**Audience:** [Who must be able to use it, including the least-prior-knowledge lens.]
**Top jobs:** [Two to four things users need to do, decide, or recover from.]
**Approach:** [Recommended content molecule or structure and why.]
**To confirm:** [Material facts, names, links, eligibility, or constraints.]
```

Keep the plan short enough for a non-designer to scan. Avoid workflow diagrams, personas, and internal project language.

After the plan, ask zero to two high-priority clarifying questions. Ask none if the plan is already complete and the only decision is whether to proceed. Ask two only when both answers are likely to change the structure, facts, or eligibility. Do not use the plan as a questionnaire.

End the plan turn with “Reply with changes, or say ‘Go ahead’ to draft.” A plan-only turn may include assumptions and up to two high-priority clarifying questions, but it must not include recommended copy, revised copy, card sets, alerts, evaluation tables, or page drafts. Do not combine the plan with the requested draft unless every plan input is already supplied and the user explicitly asks for both.

If the user confirms or supplies the missing material, move directly into drafting. If the user disagrees with the plan, revise the plan before drafting. If the user gives new constraints, build on the same plan rather than restarting the analysis.

## Translating Source Material

Use source material to understand the service, collection, space, or expertise. Do not map each source sentence to a public-facing sentence.

For each source passage, identify:

- the user’s task or decision;
- the audience or eligibility condition;
- the concrete action, location, requirement, limit, or next step;
- information that is internal context, workflow, staffing, routing, or measurement.

Then decide what belongs in the copy. Institutional goals such as “predictable,” “equitable,” and “transparent” should guide the user outcome, not appear as abstract claims. For example, instead of writing “with clear expectations for access,” show what the user can do, who can do it, and what happens next.

Use approved public names and terminology when supplied. Label a proposed terminology change as unverified when it changes eligibility, audience, collection, service, space, or expertise language.
